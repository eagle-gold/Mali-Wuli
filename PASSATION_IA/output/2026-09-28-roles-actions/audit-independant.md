# Relecture indépendante — rôles par actions

28 septembre 2026. Audit du backend final en staging, après lecture de `audit-backend.md`, avec recherche des contrôles résiduels dans la source active superposée au staging. Aucun code applicatif modifié, aucune DB, requête réseau ou commande distante exécutée.

**Verdict : aucun défaut bloquant identifié dans le périmètre relu.**

- **Permissions et absence d’escalade** : `lib/roles.ts:24–35` n’accepte que les cinq codes connus, ignore tout grant inconnu et réserve les permissions rôles/statistiques au propriétaire. L’ancien MODERATEUR conserve explicitement ses permissions historiques sans acquérir ASSOCIATIONS. `authenticate` relit les grants et la version de session en base ; ni JWT ni corps de requête ne peuvent fournir les permissions.
- **Propagation aux services** : offres et événements utilisent leurs permissions propres pour leur acteur, y compris listes privées, modification/suppression, validation et médias ; la préautorisation des uploads est conservée. Associations distingue gestionnaire global et administrateur principal. Les contrôles historiques des cercles utilisent seulement `CERCLES_GERER` ; les cinq rôles proposés ne l’accordent pas. Aucun ancien test ADMIN/MODERATEUR oublié n’a été trouvé dans les voies remplacées par une permission.
- **Attribution et concurrence** : `admin-membres.service.ts:44–62` relit l’acteur propriétaire et la cible en transaction Serializable ; protège propriétaire/soi/anciens ADMIN/comptes non validés ; vérifie la révision SHA256 sur rôle, ensemble des grants et version de session. CAS sur le compte, remplacement des grants et suppression OTP sont dans la même transaction. Une erreur ne déclenche pas la révocation des sockets ; celle-ci intervient après commit. Le no-op conserve la session. L’ancien endpoint de rôle simple renvoie 409.
- **Inscriptions** : filtre GET et décision serveur limitent le délégué aux comptes ordinaires EN_ATTENTE, excluant lui-même, propriétaire, ancien MODERATEUR et tout compte ayant des grants. La transaction relit les droits du décideur ; seuls propriétaire et permission INSCRIPTIONS peuvent agir.
- **Affiliation personnelle** : `association.service.ts:174–179` refuse à tout non-propriétaire de valider sa propre affiliation, même avec ASSOCIATIONS_GERER ou une responsabilité locale. La gestion des autres affiliations reste autorisée selon la fiche. Les contrôles de statut de la demande et la mise à jour conditionnelle restent présents.
- **Migration** : `20260928210000_delegated_roles` crée uniquement `UserRoleGrant`, sa clé `(userId, code)`, l’index code et la FK User avec cascade. Le diff Prisma ajoute cette relation et ce modèle sans modifier un ancien enum ou les données existantes. Aucun backfill n’élargit les droits.

**Conditions de publication** : appliquer cette migration avant d’activer le nouveau backend, car chaque authentification lit désormais `User.rolesDelegues`. Le retour au code précédent peut conserver la table additive ; supprimer ses lignes ou la table serait une opération de données distincte. Vérifier l’identité propriétaire validée avant bascule comme pour le lot précédent.

**Limites** : revue statique indépendante. Les tests RAM de l’agent backend couvrent les permissions isolées, CAS et auto-affiliation dans les fichiers relus, mais cette revue n’a pas réexécuté ces tests ni vérifié les verrouillages Serializable sur un MySQL réel. Aucun résultat de publication en production n’est affirmé ici.
